# 后续实验计划

> 基于导师回信整理。核心调整：**将研究叙事从"谁在稀疏奖励下能达到更高成功率"转为"谁对有缺陷的奖励函数更鲁棒"**。以下四个方向对应导师提出的四个待验证点。

---

## 1. 奖励分解（Reward Decomposition）

**要回答的问题：** PPO 的 reward gain 究竟来自奖励函数的哪个成分？GRPO 为什么不跟？

**背景：** Door 任务的原始 dense reward 是多个成分的加权和（如 `passage_reward`、`door_openness_reward`、`distance_reward`、`velocity_penalty` 等）。当前实验只看总奖励，无法判断 PPO 到底在"刷"哪个成分。

**实验设计：**

- 在 `EvalMetricsWrapper` 中增加逐成分 reward logging，在每个 episode 结束时记录各 reward component 的累积值
- 复用已有的 Phase 1 模型（`ft_ppo_v2`、`ft_grpo_v2`），运行若干 rollout，分解每次 step 的 reward
- 对比 PPO vs GRPO 在各成分上的分布差异

**预期交付：**
- 一张表或柱状图：PPO vs GRPO vs Baseline 在各 reward 成分上的对比
- 确认 PPO 的高回报主要来自哪个成分（预测：`door_openness_reward` 或 `distance_reward` 这类与 success 弱相关的 dense term）
- 解释 GRPO 为何没有被该成分带偏（group-relative advantage 对该成分不敏感？）

**实施方式：** 在 Door 环境 step 后捕获 `info` dict 中 reward 各成分的当前值，在 episode 结束时将累积值写入 W&B（作为 `eval/reward_components/xxx` 系列 metric），重新 eval 已有模型即可，无需重新训练。

## 2. 第二任务复现（Reach Task）

**要回答的问题：** Reward-hacking 现象是 Door 任务的个例，还是通用规律？

**背景：** Reach 任务已经有现成的预训练模型（`humanoid-bench/data/reach_one_hand/torch_model.pt`），且 `test_reach.py` 和 `eval_reach.py` 已写好，可以直接训练。

**与 Door 的关键差异：**
- Reach 的奖励结构更"干净"（`healthy_reward` + `motion_penalty` + `reward_close` + `reward_success`）
- Baseline 成功率预期更高（预训练模型在 Reach 上应该有较高的成功率，手够到目标比推门通过容易得多）
- 导师提醒：简单的任务可能"wash out"差异——如果两个算法都能解决，就看不出谁更鲁棒

**实验设计（分两阶段）：**

### 2.1 Phase R1 — 原始 Reach 环境（Dense Reward）
- 用 `test_reach.py` 分别在 3 个 seed（如 42, 2024, 777）上运行 PPO 和 GRPO 微调
- 每个 run 大概 2M steps
- 用 `eval_reach.py` 的 `--baseline` 先评估预训练 baseline 的成功率
- 监控：`eval/success_rate`、`eval/mean_reward`、`eval/min_hand_dist`
- 如果 baseline 已经很高（>80%），则 Phase R2 是真正有区分度的测试

### 2.2 Phase R2 — 稀疏化 Reach（Oracle Reward）
- 移除 Reach 的 dense 奖励成分，只在 episode 结束时给二值奖励（hand_dist < 0.05）
- 观察 PPO 和 GRPO 在极度稀疏的奖励下是否出现类似 Door Phase 2 的分化
- 如果 GRPO 依然保持稳定而 PPO 崩溃，规律便得到复现

**实施方式：** `test_reach.py`/`eval_reach.py` 已有代码框架。需要添加 `--phase2` flag（类似 `finetune_hb.py`），在稀疏模式下将 reward 替换为 terminal success binary。每个配置跑 3 seeds。

**时间估算：** 每个 seed 约 2-4 小时（GPU），6 个配置 × 3 seeds = 18 个 runs。

## 3. 多种子稳定性验证（Multi-Seed Runs）

**要回答的问题：** 当前观察到的效果是否稳定跨种子复现？

**背景：** 当前 Door 实验的 Phase 1 和 Phase 2 各只跑了一个 seed。导师明确指出："If it's not stable across seeds it doesn't mean much."

**实验设计：**

- 对已有实验补齐 seeds：
  - Door Phase 1（dense reward）：PPO × 3 seeds, GRPO × 3 seeds
  - Door Phase 2（sparse oracle）：PPO × 3 seeds, GRPO × 3 seeds
  - 如果已有某个 seed 的结果，补跑缺少的即可
- 对 Reach 实验从一开始就跑 3 seeds
- 评估时报告 mean ± std across seeds

**实施方式：** `finetune_hb.py` 已以 seed 为必须参数。写一个 shell 脚本批量跑：
```bash
for algo in ppo grpo; do
  for seed in 42 2024 777; do
    python finetune_hb.py --algo $algo --exp_name ft_${algo}_v2_seed${seed} --seed $seed
    python finetune_hb.py --algo $algo --exp_name ft_${algo}_v3_seed${seed} --seed $seed --phase2
  done
done
```
然后在 `eval.py` 中用 `--model_file` 分别指向各 seed 的最佳模型独立评估，汇总。

**预期交付：** 跨 seed 的 mean ± std 表格，验证 PPO reward-hacking 和 GRPO 稳定性是否一致。

## 4. KL 散度与策略变化量分析（GRPO 是否"没动"？）

**要回答的问题：** GRPO 的"稳定"是因为真的鲁棒，还是因为优化幅度太小、策略几乎没离开 baseline？

**背景：** 导师指出这是"最需要小心"的问题——"222 vs 244 and 2% vs 5% could be either." 如果 GRPO 的 KL from baseline 极小，说明它只是没怎么更新，而非"聪明地选择不 reward-hack"。

**实验设计：**

### 4.1 动作分布 KL 散度
- 在同一个固定 set of observations 上，分别用 baseline、PPO 微调后、GRPO 微调后的 policy 生成动作分布
- 计算 PPO vs Baseline 和 GRPO vs Baseline 的 KL 散度（对于高斯 policy 有闭式解）
- 如果 GRPO-Baseline KL ≪ PPO-Baseline KL，说明 GRPO 确实"没动"

### 4.2 参数空间距离
- 直接计算微调后模型与 baseline 的权重 L2 距离
- 对比 PPO 和 GRPO 的参数变化幅度

### 4.3 行为层面的变化
- 在评估 rollout 中记录更多行为指标：手到门把手的距离分布、机器人躯干 x 位置分布、episode 长度分布
- 如果 GRPO 的行为分布与 baseline 几乎完全重叠，则"没动"的嫌疑很大

### 如果确认 GRPO"没动"怎么办？
- 这不一定是坏消息——可以解读为"GRPO 的优化机制（group-relative advantage）天然对错误 reward 信号不敏感，因此不会去追虚假的梯度"
- 但需要在论文中诚实讨论这一点，而非将其描述为"GRPO 学会了更鲁棒的策略"
- 可能的补救：调大 GRPO 的学习率或 KL 惩罚系数（如果有的话），看看是否能在不 reward-hack 的前提下产生有意义的策略改进

**实施方式：**
- 写一个独立的 `analyze_kl.py` 脚本：
  1. 从环境中收集一批 observations（随机 rollout baseline 收集 ~1000 个 obs）
  2. 分别加载 baseline、PPO best、GRPO best 模型
  3. 对每个 obs，计算三者的 action distribution（mean, log_std）
  4. 计算 pairwise KL 并输出分布图
- 参数距离直接在主 eval 脚本中加几行 torch 代码即可

## 关键叙事调整

**原叙事（需修正）：**
> "在稀疏奖励环境下，GRPO 是更好的微调算法，因为它能达到更高的成功率。"

**修正后叙事：**
> "当奖励函数存在缺陷（dense reward 与真实目标不完全对齐）时，PPO 会系统性地利用奖励漏洞（reward hack），而 GRPO 的 group-relative 优化机制天然对这种误导性奖励不敏感。这不是因为 GRPO '学得更好'，而是因为它'不会去学坏的'——在奖励设计不完美的现实场景中，这是一种更安全的优化策略。"

**论文可用的三个关键图表：**
1. **Reward vs Success 背离图**（已有 W&B 截图）：PPO reward ↑, success → 0; GRPO 两者平稳
2. **Reward 分解图**（待做）：展示 PPO 在多 reward 成分上具体在哪个 term 上暴涨
3. **KL 分布图**（待做）：展示 GRPO 策略变化量 vs PPO 策略变化量
